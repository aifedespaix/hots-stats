# Local dev/test environment for the replay ingestion pipeline

Date: 2026-08-31
Status: Approved (chat), pending spec review

## Goal

Give Claude (and the user) a way to run a real, automated test of the
backend replay pipeline — daemon parser → API ingest → Postgres — entirely
locally, using the real `.StormReplay` files already committed under
`debug/`, so that a change can be verified end-to-end before `git commit` /
`git push`, without needing a human to click through the app or provide
secrets by hand.

## Non-goals

- No web app end-to-end/browser tests (Playwright etc.). `apps/web` keeps
  its existing Vitest unit tests only.
- No real Google/Battle.net OAuth in tests. The pipeline under test (daemon
  → `/ingest`) authenticates with a Personal Access Token, not a session
  cookie, so OAuth is out of scope entirely.
- No CI wiring in this pass. Everything here runs locally, on demand. The
  scripts are written so wiring them into `.github/workflows/ci.yml` later
  is a small follow-up, not a rewrite.
- No byte-exact "golden output" comparison for the full 71-file replay
  corpus — that would require hand-verifying stats for 71 real games and
  would break on every legitimate parser change. Structural invariants
  (parses without error, 10 players, valid heroes, plausible duration) are
  the bar for the corpus-wide check; exact-value assertions are reserved
  for the curated fixture set used by the API integration tests.

## Architecture

Five new/changed pieces, each independently runnable and testable:

1. Test-database bootstrap (docker + env)
2. `apps/api` integration tests (Bun)
3. `daemon-python` real-replay corpus tests (pytest)
4. A one-time/manual fixture-generation script bridging 3 → 2
5. Root-level scripts + CLAUDE.md recipe tying it together

### 1. Test-database bootstrap

`docker-compose.dev.yml` already provides a Postgres container for
interactive dev (`hots_stats` database, `bun run docker:dev:up`). Reuse the
same container for tests rather than introducing a second compose file or a
Testcontainers-style dependency — it's already the established "local dev
Postgres" convention in this repo.

Add:

- A second database, `hots_stats_test`, inside that same container.
- `.env.test` at the repo root, **gitignored** (matches the existing
  `.env.*` / `!.env.example` pattern in `.gitignore`) and **generated by a
  script**, not hand-written:
  - `DATABASE_URL=postgres://postgres:postgres@localhost:5432/hots_stats_test`
  - `SESSION_SECRET` / `CLAUDE_INTERNAL_SECRET`: random hex, generated once
    by the bootstrap script (`crypto.randomBytes` or equivalent) — value
    doesn't matter since no code path under test reads them, but
    `packages/db`/`apps/api` modules that assert required env vars exist
    still need *something* set.
  - No `GOOGLE_CLIENT_ID`/`BATTLENET_CLIENT_ID`/etc. — out of scope, and
    the ingest route never touches them.
- A bootstrap script, `scripts/test-db-up.ts` (root-level, Bun), that is
  idempotent and safe to run before every test invocation:
  1. `docker compose -f docker-compose.dev.yml up -d` (no-op if already up).
  2. Wait for the `postgres` healthcheck.
  3. `CREATE DATABASE hots_stats_test` if it doesn't already exist (connect
     to the default `postgres` maintenance DB to issue this).
  4. Run `packages/db`'s existing migrator (`migrate.ts`) against
     `hots_stats_test`.
  5. Run `packages/db`'s existing seed (`seed.ts`) against
     `hots_stats_test` — **required**, not optional: `match_players.hero_id`
     is a `NOT NULL` foreign key into `heroes` with no auto-create (unlike
     maps, which `ensureMapExists()` creates on the fly), so ingest requests
     will FK-violation without the seeded hero rows.
  - Steps 3-5 write `.env.test` if it doesn't already exist (generating the
    random secrets mentioned above), otherwise reuse it — so it's an
    idempotent "make sure everything's ready" script, not a destructive
    reset.

### 2. `apps/api` integration tests

New `apps/api/test/` directory, using `bun:test` (already in use for the
one existing unit test, `spatial-layer.test.ts`).

Key design choice: call the Hono app **in-process** via `app.request(...)`
against the real test Postgres — no HTTP server process, no mocking of
`db`. This is Hono's standard test pattern and keeps the tests fast and
simple; `packages/db`'s `db` client already reads `DATABASE_URL` from the
environment, so pointing `DATABASE_URL` at `hots_stats_test` (via
`.env.test`) is the only wiring needed.

`apps/api/test/support/db.ts`:
- `resetDb()` — truncates all tables (`TRUNCATE ... RESTART IDENTITY
  CASCADE`, excluding `maps`/`heroes` which stay seeded) between tests, so
  each test starts from a known state without re-migrating.
- `seedUserWithToken()` — inserts a `users` row and a `personal_access_tokens`
  row (hashing a known raw token via the existing `hashToken()` from
  `apps/api/src/lib/tokens.ts`), returns `{ userId, rawToken }` for use as
  `Authorization: Bearer <rawToken>`.

`apps/api/test/fixtures/replays/*.json` — real `ReplayPayload` JSON bodies,
one per curated replay (see §3/§4 below), committed as small text files.

Test coverage (`apps/api/test/ingest.test.ts`):
- POST `/ingest` with a valid fixture payload → `201`, `upserted: true`;
  follow-up query via Drizzle confirms `matches` row, 10 `match_players`
  rows with resolved `hero_id`s, and (for a multi-layer-map fixture)
  `match_spatial_grids` rows tagged with the right layer.
- POST the same payload again → `200`, `upserted: false` (no-op path).
- POST a payload with an unrecognized `m_baseBuild` → `202`,
  `quarantined: true`, and a row lands in `raw_replays_quarantine`.
- POST without a bearer token / with a revoked token → `401`.

### 3. `daemon-python` real-replay corpus tests

New `daemon-python/tests/test_replay_corpus.py`.

A shared constant (e.g. `CURATED_REPLAYS` in a small `tests/corpus.py`
helper, imported by both this test file and the fixture-dump script in §4)
lists ~8-10 filenames from `debug/`, chosen for variety:
- A handful of different maps.
- One multi-layer map (Braxis Holdout or Haunted Mines) to exercise the
  layered spatial extraction path mentioned in recent commits.
- One `Bac à sable (...)` custom/sandbox game — expected to raise
  `ReplaySkipped`, exercising that path deliberately.
- One of the most recent files, for latest-known-build coverage.

Default run (`pytest -q`, no marker needed) parses only this curated set
and asserts, per file, the same structural checks
`scripts/diagnose_replay_corpus.py` already prints as a report — turned
into real `assert`s here: parses without an unexpected exception (or raises
`ReplaySkipped` for the sandbox file, which is asserted explicitly rather
than treated as a failure), exactly 10 players, every player resolves to a
non-null hero id, `m_baseBuild` present, match duration > 0.

A second test, marked `@pytest.mark.full_corpus` and excluded by default
(`pytest.ini`'s `addopts = -m "not full_corpus"`), sweeps every
`*.StormReplay` file directly under `debug/` (all 71 today) with the same
assertions. Run by hand (`pytest -m full_corpus`) after a parser change,
not part of the fast default loop — mirrors how `diagnose_replay_corpus.py`
is already used today, just as an assertion-based regression check instead
of a printed report.

### 4. Fixture-generation script

`daemon-python/scripts/dump_fixture_payloads.py`: imports `CURATED_REPLAYS`
from `tests/corpus.py`, runs the real `parser.parse_replay()` (not a
reimplementation — same principle as `diagnose_replay_corpus.py`) on each,
and writes the resulting payload as formatted JSON to
`apps/api/test/fixtures/replays/<slug>.json`.

Run once now, as part of implementing this design, to populate the fixture
set apps/api's tests depend on. Re-run by hand only when the parser's
output shape changes and fixtures need refreshing (same maintenance model
as `diagnose_hero_mapping.py` and the other scripts in that directory) —
this is a deliberate, reviewable regeneration (the diff shows exactly what
changed in the payload shape), not something that happens automatically.

### 5. Tying it together

Root `package.json` gets:
- `test:db:up` → `bun run scripts/test-db-up.ts` (the bootstrap from §1).
- `test:api` → runs `test:db:up`, then `bun test` inside `apps/api` with
  `.env.test` loaded (Bun's `--env-file=../../.env.test` or equivalent).

`daemon-python`'s `pytest -q` needs no new script — the corpus test reads
directly from `../debug/` relative to the repo root, no DB/docker
dependency (parser tests never touch Postgres).

CLAUDE.md's Commands section gets one new line documenting the pre-push
recipe:

```bash
bun run typecheck && bun run build && bun run test:api   # from repo root
pytest -q                                                 # from daemon-python/
```

## Data flow (the thing actually being tested)

```
debug/*.StormReplay (real files, git-committed)
        │  (parser.parse_replay, real code — daemon-python)
        ▼
ReplayPayload  ──────────────► dumped once to apps/api/test/fixtures/*.json
        │                              │ (committed, reused by API tests)
        │ (only in daemon-python's                 │
        │  own corpus test — structural             ▼
        │  assertions only)              apps/api ingestRoute.request("/ingest", …)
        ▼                                        │ (real code — replay-ingest.service.ts,
   assert no crash,                              │  adapters, replay-upsert.service.ts)
   10 players, valid                             ▼
   heroes, etc.                          hots_stats_test (real Postgres, via docker)
                                                  │
                                                  ▼
                                     assert matches/match_players/spatial rows
```

The two test suites are independent (daemon tests never touch Postgres;
API tests never touch a `.StormReplay` file or the Python parser) but
together cover the whole path — the split mirrors the codebase's own
adapter boundary (`ParsedReplayData`/`ReplayPayload` in
`packages/shared-types`) between "parsing a replay" and "ingesting a
payload."

## Error handling / isolation

- `resetDb()` between `apps/api` tests keeps them order-independent and
  re-runnable without re-migrating.
- `test-db-up.ts` is idempotent — safe to run before every `test:api`
  invocation, including in a fresh checkout with no `.env.test` yet.
- The curated replay list is a single source of truth (`tests/corpus.py`),
  so the corpus test and the fixture-dump script can't drift apart on
  *which* files are "the curated set."
- If a fixture JSON goes stale relative to the current parser output (e.g.
  someone changes `ReplayPayload`'s shape without re-running
  `dump_fixture_payloads.py`), the `apps/api` tests fail loudly on a schema
  mismatch — that's a deliberate tripwire, not a bug to guard against.

## Testing the harness itself

This design's own correctness is demonstrated by successfully running:
- `bun run test:api` twice in a row on a clean checkout (proves
  idempotent bootstrap + `resetDb()` isolation).
- `pytest -q` in `daemon-python` (fast, curated set).
- `pytest -m full_corpus` in `daemon-python` at least once during
  implementation, to confirm the full 71-file `debug/` corpus parses
  cleanly against current `main` before relying on the curated subset day
  to day.

No new test framework or CI system is introduced — everything rides on
`bun:test` and `pytest`, already the project's two test runners.
